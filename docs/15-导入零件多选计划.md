## 1. 背景与目标

### 1.1 现状

| 项 | 现状 | 位置 |
|---|---|---|
| 菜单入口 | 「导入零件 JSON…」单个菜单项 | [menu.js](../src/ui/menu.js#L70-L124) |
| 文件选择 | 桌面端先试 `require('electron').remote.dialog`（**永不成功**），再回落 `Blockbench.import` | [menu.js](../src/ui/menu.js#L81-L121) |
| 多选 | **不支持**：回落调用没传 `multiple` | [menu.js](../src/ui/menu.js#L108-L111) |
| 单文件导入 | 解析 → 冲突对话框 → 写入 → 落盘 → 刷新 → toast | [drag_import.js](../src/import/drag_import.js#L70-L215) |
| 多文件导入 | 只有拖拽路径会走到；菜单是 `for` 循环逐文件调 `importPartFromPath` | [menu.js](../src/ui/menu.js#L98-L120)、[drag_import.js](../src/import/drag_import.js#L226-L305) |
| 撤销粒度 | 菜单：每文件一条；拖拽：**有冲突时**退化为每文件一条 | [drag_import.js](../src/import/drag_import.js#L388-L393) |

### 1.2 目标

1. **桌面端**文件选择器支持一次选多个 `.json`（插件 `variant: 'desktop'`，见 [plugin.js](../src/plugin.js#L25-L31) 与 `bbplugin.json` 的 `"target": "desktop"`）。
2. 整批导入只产生**一条**撤销记录：`Ctrl+Z` 一次全退，`Ctrl+Y` 一次全回。
3. 冲突**只询问一次**，策略对整批生效（覆盖 / 跳过 / 自动重命名 / 取消）。
4. 单个文件失败（坏 JSON / 非零件定义 / 非法 partId / 读盘失败 / 空内容）不中断整批，其余照常导入并**一条**汇总提示。
5. 菜单多选与拖拽复用同一条编排管线，行为一致。
6. 模块只保留**有调用方**的导出：`registerDragImport` / `unregisterDragImport` / 新增 `importParts`。现有 `importSingleFile` / `importPartFromPath` 在菜单改造后零调用方（§4.7），一并删除。

### 1.3 非目标

- **不动**导入的解析管线：仍是 `PartCodec.decode` + `resolveBoneReferences`，不切到 `ops.importPart` 的 `doc` 投影通道（§8.4）。
- 不做"导入整个目录"、"从内容包拖入"等新入口。
- **Web 端不列入验收**（`variant: 'desktop'`）。代码保持 Web 安全（用 `FileResult.content`），但这是防御性兼容。
- 不新增 MCP 工具；`mcp/tools.js` 的 `import_part` 走 `ops.importPart`，不受影响。
- 不做"内容查重"（同内容不同文件名视为两个零件）。
- 不给 `runConfigEdit` 增加"是否入栈"的返回位（core 改动，见 §4.6）。

## 2. 调研结论：为什么现在只能单选

### 2.1 Electron 原生分支是死代码

[menu.js](../src/ui/menu.js#L81-L105) 的逻辑是"先拿 `require('electron').remote`，有就调原生 `showOpenDialog`（这里其实已经写了 `multiSelections`）"。

这个分支在 Blockbench 5.x 下**永远进不去**，两个独立原因：

1. **API 不存在**：Blockbench 5.0.7 依赖 Electron `^38.1.0`（`package.json`），`remote` 模块自 Electron 14 起已移除。
2. **模块被白名单拦截**：插件的 `require` 是 Blockbench 的 scoped require（`new Function('requireNativeModule', 'require', code)` 注入，见 [plugin_loader.ts:678-689](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/plugin_loader.ts#L678-L689)），只放行
   `SAFE_APIS`（`path/crypto/events/zlib/timers/url/string_decoder/querystring/constants/buffer`）与
   `REQUESTABLE_APIS`（`fs/process/child_process/https/net/tls/util/os/v8/dialog/clipboard`），
   其余模块直接 `throw 'The module "electron" is not supported'`
   （[native_apis.ts:33-97](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/native_apis.ts#L33-L97)）。
   `'electron'` 不在名单里 → `catch` → `remote = null`。

所以在装好的插件里，"带 `multiSelections` 的原生对话框"这 20 多行是纯粹的噪音代码，每次点击还要抛一次异常再吞掉。

### 2.2 回落分支缺少 `multiple`

[menu.js](../src/ui/menu.js#L108-L121) 的回落调用只传了 `extensions`、`type`、`read_mode`。

Blockbench 的 `Blockbench.import(options, callback)`（别名 `importFile`，[api.ts:374-378](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/api.ts#L374-L378)）的 `ImportOptions` 明确支持多选：

```ts
// js/file_system.ts:53-74 / 81-149
multiple?: boolean          // 桌面端 push('multiSelections')；Web 端 input.multiple = true
readtype?: 'buffer'|'binary'|'text'|'image'|'none'|((file) => ReadType)
resource_id?: ResourceID    // 记住该资源类型上次打开的目录（StateMemory 'dialog_paths'）
```

Blockbench 自己也这么用（[io.js:530-544](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/io/io.js#L530-L544)）。我们没传 → 原生对话框就是单选。

**结论：多选能力一直是现成的，只是没打开。**

### 2.3 顺带发现的两个小问题

| 问题 | 说明 | 影响 |
|---|---|---|
| `read_mode` 是笔误 | 选项真名是 `readtype`；默认值就是 `text`（[file_system.ts:179-181](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L179-L181)），所以现在"碰巧"是对的 | 无功能影响，但会误导后续维护 |
| 已读到的内容被丢弃 | 回调里 `FileResult` 已含 `content`（[file_system.ts:241-245](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L241-L245)），代码却拿 `files[i].path` 再走 `importPartFromPath` 读一次盘 | 多一次 IO；Web 端 `path` 只是文件名（[file_system.ts:267-272](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L267-L272)），重读必失败 |

### 2.4 批量语义现状（比"多选"更值得修）

| 场景 | 现状 | 问题 |
|---|---|---|
| 菜单选 3 个文件 | `for` 循环逐文件 `importPartFromPath` | 3 条撤销记录、3 次 `saveConfig()`、3 次 `refreshOutlinerIcons()`、3 个 toast |
| 3 个文件里有 1 个 ID 已存在 | 每个冲突文件各弹一个 async Dialog | 对话框叠栈；用户要连续点两次 |
| 拖拽 3 个文件（无冲突） | 外层 `runConfigEdit('批量导入零件')` + 内层嵌套 | 撤销正确（一次回退整批）✅ |
| 拖拽 3 个文件（有冲突） | 外层 edit 在对话框确认前就 `mutate` 返回 → 空快照被丢弃；真正写入发生在对话框回调里 | **撤销退化为每文件一条**，与注释不符 |

原因：`runConfigEdit` 的 `mutate` 必须同步完成（[undo.js](../src/core/undo.js#L491-L575)），而 `showConflictDialog` 是异步的（[conflict_dialog.js](../src/import/conflict_dialog.js#L54-L78)）。[docs/13 风险表](./13-业务逻辑层与配置文档API.md#L1454) 已登记过这条缺陷与方向（"冲突决策提前到开记录前"）。

## 3. 方案对比

| 方案 | 改动量 | 多选 | 撤销粒度 | 冲突交互 | 备注 |
|---|---|---|---|---|---|
| **A. 只加 `multiple: true`** | ~3 行 | ✅ | 每文件一条 | 仍逐文件弹窗 | 能选多，但批量体验与撤销都不合格 |
| **B. 统一入口 + 批量编排**（推荐） | ~230 行 | ✅ | 整批一条 | 一次对话框，策略对整批生效 | 菜单与拖拽共用一条管线 |
| **C. 导入预览对话框** | ~400 行 | ✅ | 整批一条 | 逐项勾选 + 逐项策略 | 体验最好，后续迭代 |

## 4. 详细设计

### 4.0 状态模型、真值表与后置条件

**状态判定**（存在性必须用自有属性判断，见 §6）：

| 状态 | 判据 |
|---|---|
| `existing` | `Object.prototype.hasOwnProperty.call(existingParts, partId)` |
| `duplicate` | 本批更早的条目已有同 `partId`（**不论** `existingParts` 是否也有） |
| `new` | 其它（不在 `existingParts`，且本批首个该 `partId`） |

判定顺序：**先查本批已出现的 `partId`（→ `duplicate`），再查 `existingParts`（→ `existing`），否则 `new`**。即 `duplicate` 优先于 `existing`（`parts={a}` 且本批两次 `a.json` 时，第二条是 `duplicate` 而不是第二个 `existing`）。

`duplicate` 不弹框、不参与 `existingIds`；它**跟随同批 leader（第一个同 `partId` 的条目）的有效动作**：

| # | 状态 | 用户选择 | `action` | `finalId` | 写入 | 说明 |
|---|---|---|---|---|---|---|
| 1 | new | 无冲突不弹框 | `create` | `partId` | 是 | |
| 2 | new | 选了 overwrite / rename / skip（因批内别处有冲突） | `create` | `partId` | 是 | 三种策略都**只作用于 existing**，不牵连新增文件 |
| 3 | existing | overwrite | `overwrite` | `partId` | 是（整件替换） | |
| 4 | existing | skip | `skip` | `partId` | 否 | |
| 5 | existing | rename | `rename` | `reserve(partId)` | 是（新 key） | 如 `a` → `a_1`；**绝不占用 `config.parts` 里任何已有 key** |
| 6 | existing | cancel | `cancel` | — | 否 | 整批不写；toast「已取消导入」 |
| 7 | duplicate（leader=new，或 leader=existing 选 overwrite/rename） | 任意 | `rename` | `reserve(partId)` | 是 | 首条写 `partId`，副本改名 |
| 8 | duplicate（leader=existing 选 skip） | skip | `skip` | — | 否 | 避免"只有 `a_1` 没有 `a`" |
| 9 | duplicate（leader=existing 选 cancel） | cancel | `cancel` | — | 否 | |

**后置条件**（`expectPlanInvariants(resolved, plan)`，§7.1 每条用例都调用）：

1. `written = entries.filter(e => ['create','overwrite','rename'].includes(e.action))`；
2. `written` 的 `finalId` 两两不同；
3. `written` 中每个 `finalId` 都通过 `keys.isSafePartId`；
4. 对 `written` 中每一条：**要么** `action === 'overwrite' && finalId === partId`（它就是那个既有零件的替换目标），**要么** `finalId ∉ plan.takenIds`（不能落在配置里任何既有 key 上，无论它在不在本批）；
5. 非 cancel 决议下，`state === 'new'` 的条目 `finalId === partId`（cancel 不写，`finalId` 为空）；
6. `action === 'cancel'` 时 `written.length === 0`；
7. `written` 中每条的 `finalId` 非空（`skip` / `cancel` 允许为空）；
8. 每个 `duplicate` 条目的 `partConfig` 与 leader **不是同一对象**（保证 `resolveBoneReferences` 不会写串 marker）。

> 条件 4 是 v4 新增的关键不变量。v3 只保证"本批内不撞"，但改名结果可能撞上**批次外**的既有 key（例如 `config.parts` 已有 `a` 与 `a_1`，本批只选了 `a.json`；v3 的 `used={a}` → 取 `a_1`，静默覆盖用户没提到的那个零件）。

### 4.2 两个纯策略函数（`src/services/import_plan.js`）

#### 4.2.1 输入契约与失败归属

失败分两段产生，**`planImports` 永远看不到 I/O 结果**：

| 阶段 | 位置 | 产出 |
|---|---|---|
| 归一化（唯一 I/O 点） | `drag_import.normalizeInputs(files)` | `inputs` / `ignored`（非 `.json`）/ `failures`（`read_failed`、`empty_content`） |
| 纯策略 | `import_plan.planImports(inputs, existingParts)` | `entries` / `failures`（`bad_json`、`bad_part`、`bad_part_id`）/ `existingIds` / `duplicateIds` / `takenIds` |

```js
// drag_import.js
/** @returns {{inputs: Array<{name, content, path?}>, ignored: number,
 *             failures: Array<{fileName, reason: 'read_failed'|'empty_content'}>}} */
function normalizeInputs(files) { ... }

// services/import_plan.js
/**
 * @param {Array<{name: string, content: string, path?: string}>} inputs
 * @param {Object<string, any>} existingParts   // config.parts（只读，不修改）
 * @returns {{
 *   entries: Array<{
 *     fileName: string, partId: string, partConfig: Object,
 *     state: 'new'|'existing'|'duplicate',
 *     leaderIndex: number|null   // 第一个同 partId 的 entries 下标；仅 duplicate
 *   }>,
 *   failures: Array<{fileName, reason: 'bad_json'|'bad_part'|'bad_part_id', detail?: string}>,
 *   existingIds: string[],      // 去重，仅用于冲突对话框
 *   duplicateIds: string[],     // 去重，仅用于汇总提示
 *   takenIds: string[]          // Object.keys(existingParts)，resolvePlan 的占位初值
 * }}
 */
function planImports(inputs, existingParts) { ... }
```

`leaderIndex` 的基准是 **`entries` 数组下标**（失败文件不进 `entries`），取**第一个**同 `partId` 的条目（3 份同名时后两份都指向第 0 条，形成链）。每个 entry 的 `partConfig` 来自各自独立的 `PartCodec.decode`，不共享对象。

#### 4.2.2 解析与校验规则

| 输入 | 结果 |
|---|---|
| 文件名不是 `.json`（大小写不敏感） | 计入 `ignored`（**不静默**：汇总文案会写"忽略 N 个非 JSON"） |
| 缺 `name` | 用 `path` 的 basename 兜底；两者都缺 → `read_failed` |
| `content === ''` | `empty_content`（`normalizeInputs` 产出） |
| 无 `content` 且读盘抛错 | `read_failed`（`normalizeInputs` 产出） |
| `parseJSONWithComments` 抛错 | `bad_json` |
| `PartCodec.decode` 抛错（非对象/数组/字段类型不符） | `bad_part` |
| 解码后 `variants` **不是非空对象** | `bad_part` |
| `keys.isSafePartId(partId)` 不通过 | `bad_part_id` |

**"`variants` 非空"的依据**：[validate.js](../src/services/validate.js#L251-L257) 把"零件没有定义变体"判为 `MISSING_REQUIRED`。导入侧采用同一条**第一道**判据，保证不产生零变体零件。注意这不是"与导出闸门完全同源"——`validate` 还要求 `model`、`sub_parts`、`hit_boxes`、`mass` 等，导入不会全部前置校验，导进来的零件仍可能在导出时被拦（这是既有行为，不在本次范围）。

为什么必须显式判：`PartCodec` 的 **9 个字段全部带默认值**（[part_codec.js](../src/codec/codecs/part_codec.js#L37-L56)；文件头注释写"12 字段"是存量笔误，本次顺手改 9），而 `Codec.record.decode` 宽松到"任何对象都能解出全默认零件并保留未知字段"（[Codec.js](../src/codec/Codec.js#L412-L436)）。误选一个 connector JSON 不会抛错，会静默写成"零变体空零件"。

**单变体简写必须被接受，但简写在 `variants` 内部**：单变体零件导出为

```json
{ "variants": { "model": "machine_max:model/hull", "textures": { "default": "..." }, "tags": [] } }
```

`Codec.either` 对 `variants` 的**值**做 `typeof raw.model === 'string'` 判定，命中则包装成 `{default: variant}`（[Codec.js](../src/codec/Codec.js#L575-L606)），`Object.keys(variants)` 为 `["default"]` → 通过。必须有用例钉住，防止后续改动误伤。

反例（实测，**勿**写成夹具）：顶层 `{"model": "...", "textures": {...}}` 会被解码成 `variants: {}` → `bad_part`。顶层 `model` 不是任何合法零件的存储形态，不做归一化。

#### 4.2.3 `resolvePlan(plan, action)`

```js
/**
 * @param {ReturnType<typeof planImports>} plan
 * @param {'overwrite'|'skip'|'rename'|'cancel'} action
 * @returns {{ entries: Array<{...planEntry, action: string, finalId: string|null}>,
 *             cancelled: boolean }}
 */
function resolvePlan(plan, action) { ... }
```

**分配算法（两遍）**：

```
① used = new Set(plan.takenIds)          // ★ 全部既有 key，不是本批 existingIds
② 第一遍：所有 state === 'new' → finalId = partId，used.add(partId)
③ 第二遍：按 entries 顺序
     existing + overwrite → finalId = partId
     existing + skip      → finalId = partId（不写）
     existing + rename    → finalId = reservePartId(partId, used)
     duplicate            → 看 leader 已决 action：
                            skip/cancel → 同 skip/cancel
                            否则 → finalId = reservePartId(partId, used)
     得到 finalId 时 used.add(finalId)
④ action === 'cancel' → 全部 action='cancel'，cancelled=true
```

两个必须两遍/全量播种的理由：

- **两遍**：`new` 条目的 `partId` 在分配前既不在 `takenIds`（它不在配置里）、也还没被"分配"。v2 单遍写法的反例：`config.parts={b}`，本批 `b.json`(existing) + `b_1.json`(new)，选 rename → 处理 `b` 时 `used={b}` → 取 `b_1` → 与后处理的 new `b_1` 相撞。
- **全量 `takenIds`**：只播种本批 `existingIds` 时，改名会撞上**批次外**的既有 key。反例：`config.parts={a, a_1}`，本批只选 `a.json`（existing）选 rename → `used` 若是 `{a}` → 取 `a_1` → 覆盖用户没提到的零件。v3 的写法正是这个 bug。

副作用是编号会"跳号"：`config.parts={b}` + 本批 `b.json`/`b_1.json` 选 rename ⇒ `b` 变成 `b_2`（`b_1` 被本批 new 占用）。已在 §5 与对话框文案里说明。

#### 4.2.4 `reservePartId(base, used)`（`src/doc/keys.js`）

```js
keys.reservePartId('a'.repeat(128), used)  // → 'a'.repeat(126) + '_1'
```

- **前置条件**：`base` 必须已通过 `keys.isSafePartId`；否则立即抛 `TypeError`（`planImports` 已把非法 partId 归入 `bad_part_id`，正常路径不会触发）。不写这条的话，非法 base 会让 `truncateNameForSuffix` 返回 `''`、候选变成 `_1`、`split('_')[0]===''` 判非法，然后空转 9999 次。
- **契约**：永远返回合法、未被占用的 id，**不返回 `null`**。
- 从 `_1` 起（与现有 `generateUniqueId` 语义一致）；候选 = `truncateNameForSuffix(base, '_' + n) + '_' + n`，再判 `isSafePartId` 与 `!used.has`。
- 合法性可以证明：`max = 128 - len('_n') ≥ 123`，候选前缀非空且首段不变（设备名是精确匹配，不可能被前缀"造"出来），尾点被剥、`_n` 覆盖下划线结尾。
- 理论上只有 `used` 里已占满 9999 个候选才会耗尽；那时直接抛错（属于调用方数据异常，且在 `runConfigEdit` 之前，不会半写）。

`truncateNameForSuffix` 现在存在但**未导出**（[keys.js](../src/doc/keys.js#L319-L325)、导出清单 L484-L516），本次一并导出。

### 4.3 编排：`importParts` / `applyPlan`

**并发 guard**：同一时刻只允许一条导入流程（否则两批会各自按旧快照分配同一个 `a_1`，后者覆盖前者；`new Dialog({id:'mm_import_conflict'})` 的固定 id 也可能直接冲突）。

```js
var _importing = false;   // 模块级

function importParts(files) {
    if (_importing) { showToast('已有导入流程在进行中，请先完成或取消', 'warning'); return; }
    _importing = true;
    try {
        var config = getConfig();                 // 先判项目，避免无项目时白读盘
        if (!config) { _importing = false; showToast('请先打开项目', 'warning'); return; }

        var norm = normalizeInputs(files);        // {inputs, ignored, failures}
        var plan = importPlan.planImports(norm.inputs, config.parts || {});

        if (!plan.entries.length) {               // 全非 json / 空输入：只有真失败才提示
            _importing = false;
            var failures = norm.failures.concat(plan.failures);
            if (failures.length) showToast(summaryText({ failures: failures, ignored: norm.ignored }), 'error');
            return;
        }

        if (plan.existingIds.length) {            // 只对 existing 弹一次
            showConflictDialog({
                typeLabel: '零件',
                conflictIds: plan.existingIds,
                isBatch: plan.entries.length > 1 || plan.existingIds.length > 1,
                entryCount: plan.entries.length,
            }, function (action) {
                applyPlan(norm.inputs, norm.failures, action, config, norm.ignored);
            });
            return;                               // guard 由 applyPlan 释放
        }

        applyPlan(norm.inputs, norm.failures, 'overwrite', config, norm.ignored);
    } catch (err) {
        _importing = false;
        throw err;
    }
}
```

```js
function applyPlan(inputs, normFailures, action, entryConfig, ignored) {
    try {
        if (action === 'cancel') { showToast('已取消导入'); return; }

        var config = getConfig();                 // 对话框是异步的：必须重新取
        if (!config) { showToast('项目已关闭，导入取消', 'warning'); return; }
        if (config !== entryConfig) { showToast('项目已切换，导入取消', 'warning'); return; }

        // ★ 用最新的 config.parts 重新规划：避免对话框期间新增的零件被无视
        var plan = importPlan.planImports(inputs, config.parts || {});
        var failures = normFailures.concat(plan.failures);
        var resolved = importPlan.resolvePlan(plan, action);

        var writable = resolved.entries.filter(function (e) {
            return e.action === 'create' || e.action === 'overwrite' || e.action === 'rename';
        });
        if (!writable.length) {                   // 全跳过：先判空，不进撤销栈
            showToast(summaryText({ skipped: resolved.entries.length, failures: failures, ignored: ignored }), 'info');
            return;
        }

        // 编辑器有未完成的原生编辑时，runConfigEdit 会走"不记录"分支（无回滚）——提前规避
        if (undo.isEditInProgress && undo.isEditInProgress()) {
            showToast('编辑器有未完成的操作，请稍后重试', 'warning');
            return;
        }

        var unresolvedTotal = 0;
        try {
            undo.runConfigEdit('导入 ' + writable.length + ' 个零件', function () {
                if (!config.parts) config.parts = {};
                for (var i = 0; i < writable.length; i++) {
                    var e = writable[i];
                    config.parts[e.finalId] = e.partConfig;
                    resolveBoneReferences(config, e.finalId);
                    unresolvedTotal += (e.partConfig._unresolved_bones || []).length;
                }
            });
        } catch (err) {
            log.error('applyPlan: 批量导入失败', err);
            showToast('导入失败：' + (err && err.message ? err.message : '未知错误')
                + '（若未自动回滚，请 Ctrl+Z 或重新打开项目）', 'error', 5000);
            return;                               // 不 flush、不 setActive、不报成功
        }

        var active = config._uiState && config._uiState.activePartId;
        if (!active || !config.parts[active]) {
            ops.setActive(config, { partId: writable[0].finalId, source: 'import' });
        }

        flushSave();                              // 清掉 mm_config_changed 排的防抖，单写
        try { require('../mode/icons.js').refreshOutlinerIcons(); } catch (e) { /* 面板未挂载时兜底 */ }
        showToast(summaryText({
            written: writable.length,
            skipped: resolved.entries.length - writable.length,
            failures: failures,
            ignored: ignored,
            unresolved: unresolvedTotal,
        }), unresolvedTotal ? 'warning' : 'positive', 5000);
    } finally {
        _importing = false;
    }
}
```

要点：

- **`runConfigEdit` 内只做同步写入**：不弹框、不读盘、不 toast、不落盘；
- **无嵌套 `runConfigEdit`**：撤销边界完全由 `applyPlan` 持有；
- **回调内重新规划**：`plan` 只在弹框前用于展示冲突；真正的 `finalId` 基于确认时的 `config.parts` 计算；
- **`config.parts` 只在写入时创建**：弹框/取消路径不碰配置对象（否则 §5 的"整批不写"与测试断言都不成立）；
- **`flushSave()` 而不是 `saveConfig()`**：`mm_config_changed` 已会 `scheduleSave()`（[App.vue.js](../src/ui/App.vue.js#L1780-L1796)），再 `saveConfig()` 就是写两次；
- **`refreshOutlinerIcons` 是兜底**：`ops.setActive` 与 `runConfigEdit` 都会派发事件，面板挂载时事件已刷新；显式再调一次是幂等的，用来覆盖"面板未挂载"的场景；
- 汇总 toast 只发一次：失败明细进日志，文件名超过 3 个截断。

**文案矩阵**（`summaryText({written, skipped, failures, ignored, unresolved})`）：

| 场景 | 判定 | 文案 |
|---|---|---|
| 有写入、干净 | `written > 0`，无 skipped/failures/ignored/unresolved | `已导入 3 个零件` |
| 有跳过 | `skipped > 0` | `已导入 3 个零件（跳过 1）` |
| 有失败 | `failures.length` | `已导入 3 个零件（失败 2：a.json、b.json）` |
| 有忽略 | `ignored > 0` | `已导入 3 个零件（忽略 1 个非 JSON）` |
| 有未解析骨骼 | `unresolved > 0` | `已导入 3 个零件（7 个骨骼未在大纲树中找到）` |
| 全跳过 | `written === 0 && skipped > 0` | `已跳过 3 个零件` |
| 全失败 | `!entries.length && failures.length` | `无法导入：2 个文件解析失败` |
| 无条目无失败 | 空选择 | **不弹** |

多条件同时成立时按 "失败 / 忽略 / 跳过 / 未解析" 依次拼接，括号内用 `；` 分隔。

## 5. 交互语义约定

| 场景 | 行为 |
|---|---|
| 整批无冲突、全部成功 | 一条 toast：`已导入 5 个零件` |
| 部分文件解析失败 | 其余照常导入；toast：`已导入 3 个零件（失败 2：a.json、b.json）`；失败原因进日志 |
| 全部解析失败 | 不产生撤销记录，一条错误 toast：`无法导入：2 个文件解析失败` |
| 混入非 JSON | 计数进 `ignored`，汇总文案列出"忽略 N 个非 JSON"；**不静默丢文件** |
| 全部被扩展名过滤 / 空输入 | **静默**（不弹 toast） |
| 存在冲突 | **只弹 1 个**对话框；策略对整批生效 |
| 用户选 skip | **只跳过与现有零件冲突的文件**；本批新增零件、以及它们的同名副本仍按 leader 写入/改名 |
| 用户选 overwrite | 覆盖既有零件；批内同名副本仍改名（不覆盖同一个 key 两次） |
| 用户取消对话框 | **整批不写**（含未冲突文件），配置对象不被改动，toast「已取消导入」 |
| 全部跳过（本批全部冲突） | 无撤销记录、无落盘、无刷新，toast `已跳过 3 个零件` |
| 批内同名文件 | 首条按规则处理，副本按 leader 结果自动改名；**改名跳过配置里所有已占用 key**（例如内容包已有 `b_1` 时，`b` 重命名为 `b_2`） |
| 有骨骼未解析 | 汇总进同一条 toast：`已导入 4 个零件（7 个骨骼未在大纲树中找到）` |
| 写入过程中抛错 | 记录态下整批回滚；toast `导入失败：<原因>`，无撤销记录，`_uiState` 不动；若是"未记录"分支（编辑器忙 / 超 2 MB），toast 提示可能需要手动检查 |
| 对话框未关时切换了工程 | 整批放弃，toast `项目已切换，导入取消` |
| 已有导入流程未结束 | 第二次导入直接拒绝，toast `已有导入流程在进行中…` |
| 覆盖内容与既有完全一致 | 不产生撤销记录（空变更被丢弃），仍刷新并提示"已导入" |
| 撤销 | 整批一条：`Ctrl+Z` 全退，`Ctrl+Y` 全回 |

## 6. 边界与失败处理

| 边界 | 处理 |
|---|---|
| Web 端（无 `fs`） | 完全依赖 `FileResult.content`；`content` 缺失且无 `path` → `read_failed`。仅作防御，不验收 |
| `content` 不是字符串（Buffer 等） | 传 `undefined` 让 `normalizeInputs` 用 `path` 回退（§4.4） |
| 缺 `name` | 用 `path` basename；两者都缺 → `read_failed` |
| **`constructor.json` 等原型键** | `config.parts` 是普通对象，`parts['constructor']` 经原型链返回函数。存在性必须用 `Object.prototype.hasOwnProperty.call`（`in` 同样不行）；写入侧同样用自有属性断言 |
| 桌面端文件被锁/被删 | Blockbench 的 `readFile` 在 `readFileSync` 抛错时不自增计数，`callback` 可能永不触发（[file_system.ts:213-249](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L213-L249)）。不绕过 BB 读取；文档记录，现场复现再加超时提示 |
| 同一批 20+ 文件 | 一次写入 + 一次快照，优于现在的 N 次 |
| 2 MB 快照上限 | 走"不记录"分支，沿用 `_runUnrecorded` 的节流提示（§4.6） |
| 并发导入 | 模块级 guard + 回调内重新规划（§4.3） |
| 对话框期间切换工程 | 引用比对，整批放弃 |
| 非法 partId | 单文件失败不阻断整批 |
| 128 长度上限 | `reservePartId` 截短 + `isSafePartId` 断言（§4.2.4） |
| 大小写/设备名 | `'A'` → 字符集拒绝；`'con'`、`'con_hull'` → 设备名/首段拒绝（[keys.js](../src/doc/keys.js#L106-L111)） |
| 单变体简写 | 见 §4.2.2：简写在 `variants` 内部，`{default:…}` 包装后非空 |

| 顶层 `{"model":"..."}`（错误形态） | `failures(bad_part)`（防止把测试夹具写错） |
| 非法 partId：`..`、`A`、`con`、`con_hull` | `failures(bad_part_id)` |
| **`constructor.json`** | 不判成 existing；`existingIds` 不含 `constructor`；正常导入 |
| 与现有 parts 冲突 | `existingIds` 含该 ID，条目 `state:'existing'` |
| 批内同名（不同目录 `a.json` ×2） | 第二条 `duplicate`、`leaderIndex:0`，`duplicateIds` 含 `a`，`existingIds` 不含 |
| **3 份同名** | 后两条都 `leaderIndex:0`（链式），rename 后三条 key 互异 |
| **批次外相邻 key（P0 回归）**：`config.parts={a, a_1}`，本批 `[a.json]` 选 rename | `finalId === 'a_2'`，**绝不等于 `a_1`** |
| 混合批：existing `b` + new `b_1` + duplicate `b.json` | rename → `{b_2, b_1, b_3}`；overwrite → `{b, b_1, b_2}`；skip → 只写 `b_1` |
| 批内同名 + overwrite（无 existing） | 首条 `create` 写 `a`，副本 `rename` 写 `a_1` |
| 批内同名 + skip（leader=existing） | 两条都 `skip`，`written` 为空 |
| `resolvePlan(plan,'cancel')` | `cancelled === true`，全部 `action:'cancel'`，`written` 空 |
| 128 长度 + 重名 | `finalId === 'a'.repeat(126) + '_1'`（**精确值**），且 `'a'.repeat(128)` 未被写成 |
| `reservePartId` 契约 | 预置 `used={a,a_1..a_5}` → 首次返回 `a_6`；连续 100 次把结果 `add` 回 `used` 仍唯一且合法；非法 base 抛 `TypeError` |
| 纯函数性 | `planImports` 前后对 `existingParts` 做 `deepEqual`；`resolvePlan` 不修改入参、连调两次结果深相等 |
| 对象独立性 | 两个 `duplicate` entry 的 `partConfig` 与 leader 不是同一引用 |
