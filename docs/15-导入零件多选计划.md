# 15 — 导入零件多选与批量导入计划

> 状态：**方案待评审（未改动任何代码）** · 日期：2026-10-25 · 范围：Blockbench 插件（不含主模组 MachineMax）
> 目标版本：`0.5.4` · 参照：[03-交互设计](./03-交互设计.md)、[11-接入Blockbench原生撤销](./11-接入Blockbench原生撤销.md)、[13-业务逻辑层与配置文档API](./13-业务逻辑层与配置文档API.md)
> 目的：把「导入零件 JSON…」从单选改为多选，并把"一次导入多个文件"变成**一条撤销记录 + 一次冲突决议 + 一条结果提示**的原子操作。

---

## 1. 背景与目标

### 1.1 现状

| 项 | 现状 | 位置 |
|---|---|---|
| 菜单入口 | 「导入零件 JSON…」单个菜单项 | [menu.js](../src/ui/menu.js#L70-L124) |
| 文件选择 | 桌面端先试 `require('electron').remote.dialog`（**永不成功**），再回落 `Blockbench.import` | [menu.js](../src/ui/menu.js#L81-L121) |
| 多选 | **不支持**：回落调用没传 `multiple` | [menu.js](../src/ui/menu.js#L108-L111) |
| 单文件导入 | 解析 → 冲突对话框 → 写入 → 落盘 → 刷新 → toast | [drag_import.js](../src/import/drag_import.js#L70-L215) |
| 多文件导入 | 只有拖拽路径会走到；菜单是 `for` 循环逐文件调 `importPartFromPath` | [menu.js](../src/ui/menu.js#L98-L120)、[drag_import.js](../src/import/drag_import.js#L226-L305) |
| 撤销粒度 | 菜单：每文件一条；拖拽：**有冲突时**退化为每文件一条 | [drag_import.js](../src/import/drag_import.js#L388-L393) |

### 1.2 目标

1. 文件选择器支持一次选多个 `.json`（桌面端与 Web 端一致）。
2. 整批导入只产生**一条**撤销记录：`Ctrl+Z` 一次全退，`Ctrl+Y` 一次全回。
3. 冲突**只询问一次**，策略对整批生效（全部覆盖 / 全部跳过 / 全部自动重命名）。
4. 单个文件失败（坏 JSON / 非法 partId）不中断整批，其余照常导入并汇总提示。
5. 菜单多选与拖拽复用同一条编排管线，行为一致。
6. 保留现有导出 API（`importSingleFile` / `importMultipleFiles` / `importPartFromPath`）不破坏调用方。

### 1.3 非目标

- **不动**导入的解析管线：仍是 `PartCodec.decode` + `resolveBoneReferences`，不切到 `ops.importPart` 的 `doc` 投影通道（两条管线语义不同，见 §8.4）。
- 不做"导入整个目录"、"从内容包拖入"等新入口。
- 不新增 MCP 工具；`mcp/tools.js` 的 `import_part` 走 `ops.importPart`，本次不受影响。
- 不重做冲突对话框的信息架构（导入预览 / 逐项选择留作后续 C 方案）。

## 2. 调研结论：为什么现在只能单选

### 2.1 Electron 原生分支是死代码

[menu.js](../src/ui/menu.js#L81-L105) 的逻辑是"先拿 `require('electron').remote`，有就调原生 `showOpenDialog`（这里其实已经写了 `multiSelections`）"。

这个分支在 Blockbench 5.x 下**永远进不去**，两个独立原因：

1. **API 不存在**：Blockbench 5.0.7 依赖 Electron `^38.1.0`（`package.json`），`remote` 模块自 Electron 14 起已移除。
2. **模块被白名单拦截**：插件的 `require` 是 Blockbench 的 scoped require（`new Function('require', code)` 注入，见 [plugin_loader.ts:678-689](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/plugin_loader.ts#L678-L689)），只放行
   `SAFE_APIS`（`path/crypto/events/zlib/timers/url/string_decoder/querystring/constants/buffer`）与
   `REQUESTABLE_APIS`（`fs/process/child_process/https/net/tls/util/os/v8/dialog/clipboard`），
   其余模块直接 `throw 'The module "electron" is not supported'`
   （[native_apis.ts:33-97](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/native_apis.ts#L33-L97)）。
   `'electron'` 不在名单里 → `catch` → `remote = null`。

所以在装好的插件里，"带 `multiSelections` 的原生对话框"这 20 多行是纯粹的噪音代码，每次点击还要抛一次异常再吞掉。

### 2.2 回落分支缺少 `multiple`

[menu.js](../src/ui/menu.js#L108-L121) 的回落调用只传了 `extensions`、`type`、`read_mode`。

Blockbench 的 `Blockbench.import(options, callback)`（别名 `importFile`，[api.ts:374-378](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/api.ts#L374-L378)）的 `ImportOptions` 明确支持多选：

```ts
// js/file_system.ts:53-74 / 81-149
multiple?: boolean          // 桌面端 push('multiSelections')；Web 端 input.multiple = true
readtype?: 'buffer'|'binary'|'text'|'image'|'none'|((file) => ReadType)
```

Blockbench 自己也这么用（[io.js:526-541](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/io/io.js#L526-L541)）。我们没传 → 原生对话框就是单选。

**结论：多选能力一直是现成的，只是没打开。**

### 2.3 顺带发现的两个小问题

| 问题 | 说明 | 影响 |
|---|---|---|
| `read_mode` 是笔误 | 选项真名是 `readtype`；不过默认值就是 `text`（[file_system.ts:179-181](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L179-L181)），所以现在"碰巧"是对的 | 无功能影响，但会误导后续维护 |
| 已读到的内容被丢弃 | 回调里 `FileResult` 已含 `content`（[file_system.ts:241-245](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L241-L245)），代码却拿 `files[i].path` 再走 `importPartFromPath` 读一次盘 | 多一次 IO；**Web 端 `path` 只是文件名**（[file_system.ts:267-272](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L267-L272)），重读必失败 |

### 2.4 批量语义现状（这是比"多选"更值得修的部分）

即使只加一个 `multiple: true`，现在的实现也会把批量导入做成"一串独立操作"：

| 场景 | 现状 | 问题 |
|---|---|---|
| 菜单选 3 个文件 | `for` 循环逐文件 `importPartFromPath` | 3 条撤销记录、3 次 `saveConfig()`、3 次 `refreshOutlinerIcons()`、3 个 toast |
| 3 个文件里有 1 个 ID 已存在 | 每个冲突文件各弹一个 async Dialog | 对话框叠栈；用户要连续点两次 |
| 拖拽 3 个文件（无冲突） | 外层 `runConfigEdit('批量导入零件')` + 内层嵌套 | 撤销正确（一次回退整批）✅ |
| 拖拽 3 个文件（有冲突） | 外层 edit 在对话框确认前就 `mutate` 返回 → 空快照被丢弃；真正写入发生在对话框回调里 | **撤销退化为每文件一条**，与注释"一次 Ctrl+Z 回退整批"不符 |

第 4 条是实现细节导致的：`runConfigEdit` 的 `mutate` 必须同步完成（[undo.js](../src/core/undo.js#L491-L569)），而 `showConflictDialog` 是异步的（[conflict_dialog.js](../src/import/conflict_dialog.js#L54-L78)）。**撤销边界必须挪到对话框之后**，否则外层的 `initEdit/finishEdit` 只会记下"什么都没改"。

## 3. 方案对比

| 方案 | 改动量 | 多选 | 撤销粒度 | 冲突交互 | 备注 |
|---|---|---|---|---|---|
| **A. 只加 `multiple: true`** | ~3 行 | ✅ | 每文件一条 | 仍逐文件弹窗 | 能选多，但批量体验与撤销都不合格 |
| **B. 统一入口 + 批量编排**（推荐） | ~150 行 | ✅ | 整批一条 | 一次对话框，策略对整批生效 | 菜单与拖拽共用一条管线 |
| **C. 导入预览对话框** | ~400 行 | ✅ | 整批一条 | 逐项勾选 + 逐项策略 | 体验最好，建议作为后续迭代 |
| **D. `require('dialog')` 走原生对话框** | ~40 行 | ✅ | 取决于编排 | 同 A/B | 需要额外申请"打开原生对话框"权限，多一次授权弹窗；`Blockbench.import` 已够用 |

**选 B**。理由：

- `Blockbench.import` 已覆盖桌面/Web 两端的多选，且支持 `resource_id` 记住上次目录，没有理由绕开它去申请新权限（排 D）；
- 多选只是入口问题，真正的痛点是撤销粒度和冲突交互（A 不解决）；
- C 的信息量对"导入零件"这种低频操作用不上，先留接口（`planImports` 的返回值天然就是预览数据）。

## 4. 推荐方案（B）详细设计

### 4.1 分层

```
src/ui/menu.js              入口：选文件（multiple）→ 交给 importParts
        ↓
src/import/import_plan.js   【新增】纯函数：解析 + 校验 + 冲突扫描 + 命名规划（无 fs / 无 Blockbench）
        ↓
src/import/drag_import.js   编排：预检 → 冲突决议（一次 Dialog）→ 一次 runConfigEdit → 收尾
        ↓
src/core/undo.js            撤销边界（沿用，不改）
```

抽纯函数的好处：`planImports` 不碰 `fs`、不碰全局 `Blockbench`，可以直接用 `bun test` 覆盖，不需要 `test/mocks/blockbench.js` 的桩。

### 4.2 `src/import/import_plan.js`（新增）

```js
/**
 * @param {Array<{name: string, content: string, path?: string}>} files
 * @param {Object<string, any>} existingParts   // config.parts
 * @param {{action?: 'overwrite'|'skip'|'rename'}} [options]
 * @returns {{
 *   entries: Array<{partId: string, finalId: string, partConfig: Object, fileName: string, conflict: boolean}>,
 *   failures: Array<{fileName: string, reason: 'bad_json'|'bad_part'|'bad_part_id'}>,
 *   conflictIds: string[]
 * }}
 */
function planImports(files, existingParts, options) { ... }
```

规则：

| 输入 | 处理 |
|---|---|
| 扩展名不是 `.json`（大小写不敏感） | 忽略，不报错（菜单过滤已挡住，拖拽可能混入） |
| `parseJSONWithComments` 抛错 | → `failures[{reason:'bad_json'}]` |
| `PartCodec.decode` 抛错 | → `failures[{reason:'bad_part'}]` |
| `keys.isSafePartId` 不通过 | → `failures[{reason:'bad_part_id'}]`（同时 toast 具体文件名与规则） |
| `existingParts[partId]` 存在 | 标记 `conflict: true`，收集进 `conflictIds` |
| 同一批内 `partId` 重复（不同目录同名文件） | 同样视为冲突，进 `conflictIds`，在 `planImports` 里按出现顺序预留新 ID |
| `finalId` 生成 | `reserveId(base, used)`：`base` → `base_1` → `base_2`……；`used` = `existingParts` 的 key ∪ 本批已分配的 `finalId`，避免批内互撞 |

`planImports` 不修改任何入参（纯函数），`partConfig` 是 `PartCodec.decode` 的产物。

### 4.3 `importParts(files)` 编排（`drag_import.js` 新增公开入口）

```js
function importParts(files) {
    var config = getConfig();
    if (!config) { showToast('请先打开项目', 'warning'); return; }
    if (!config.parts) config.parts = {};

    // ① 归一化：优先用调用方给的 content，缺失才读盘（Web 端没有 path）
    var inputs = normalizeInputs(files);            // {name, content, path}
    // ② 预检（纯函数）
    var plan = importPlan.planImports(inputs, config.parts);

    if (plan.failures.length) notifyFailures(plan.failures);   // 汇总日志 + 一条 toast
    if (!plan.entries.length) { /* 全失败：到此为止，不产生撤销记录 */ return; }

    // ③ 冲突决议（一次）
    if (plan.conflictIds.length) {
        showConflictDialog({
            typeLabel: '零件',
            defId: summarize(plan.conflictIds),   // 'a、b 等 3 个'
            isBatch: plan.entries.length > 1,
        }, function (action) {
            applyPlan(config, importPlan.resolvePlan(plan, action));  // ④
        });
        return;
    }
    applyPlan(config, plan);   // ④ 无冲突直接写
}
```

```js
function applyPlan(config, plan) {
    var written = [];
    var unresolved = 0;

    undo.runConfigEdit('导入 ' + plan.entries.length + ' 个零件', function () {
        for (var i = 0; i < plan.entries.length; i++) {
            var e = plan.entries[i];
            if (e.action === 'skip') continue;
            config.parts[e.finalId] = e.partConfig;
            resolveBoneReferences(config, e.finalId);   // 必须在写入之后
            written.push(e.finalId);
            unresolved += (e.partConfig._unresolved_bones || []).length;
        }
    });

    if (!written.length) return;                        // 全跳过：不落盘、不刷新
    saveConfig();                                       // 整批一次
    try { require('../mode/icons.js').refreshOutlinerIcons(); } catch (e) { /* 非零件模式 */ }
    showToast(summaryText(written.length, plan, unresolved), unresolved ? 'warning' : 'positive', 5000);
}
```

要点：

- **`runConfigEdit` 里只做同步写入**，不弹框、不读盘、不 toast（保持撤销边界干净）；
- 嵌套调用（内层每零件也调 `runConfigEdit`）会并入外层一条记录（[undo.js](../src/core/undo.js#L499-L506)）——这一点保持不变，但**不再依赖**它来兜异步对话框；
- `saveConfig()` / `refreshOutlinerIcons()` / toast 全部从每文件提到整批一次（现在 `_applyImport` 里每文件各做一遍）；
- 空写入（全部跳过）不落盘、不产生撤销记录。

### 4.4 `src/ui/menu.js` 改动

```js
{
    name: '导入零件 JSON…',
    click: function () {
        var config = getConfig();
        if (!config) { showToast('请先打开项目', 'warning'); return; }

        Blockbench.import({
            type: 'JSON 文件',
            extensions: ['json'],
            multiple: true,                 // ← 打开多选
            readtype: 'text',               // ← 修正 read_mode 笔误
            resource_id: 'mm_part_import',  // 记住上次目录
        }, function (files) {
            if (!files || !files.length) return;
            var inputs = [];
            for (var i = 0; i < files.length; i++) {
                inputs.push({
                    path: files[i].path || '',
                    name: files[i].name,
                    content: typeof files[i].content === 'string' ? files[i].content : '',
                });
            }
            require('../import/drag_import.js').importParts(inputs);
        });
    },
}
```

删除项：

- [menu.js](../src/ui/menu.js#L81-L105) 的 `require('electron').remote` 整段（含 `showOpenDialog` 的 `.then/.catch`）；
- 逐文件 `importPartFromPath` 循环。

保留 `importPartFromPath` 作为导出（内部改成"读盘 → `importParts([...])`"），避免外部调用方断裂。

### 4.5 冲突对话框（`conflict_dialog.js`）

改动仅限文案与批量语义，不改 API：

| 项 | 现状 | 改后 |
|---|---|---|
| 标题 | 恒为「导入冲突」 | 批量时「批量导入冲突（3 个文件已存在）」 |
| 正文 | `零件 a 已存在` | `零件 a、b 等 3 个已存在，请选择对整批的处理方式` |
| `rename` 文案 | 「重命名导入（自动追加 _1 后缀）」 | 批量时「全部自动重命名（依次追加 _1、_2…）」 |
| 取消 | `onResolve('skip')` | 不变（= 全部跳过） |

### 4.6 撤销与事件

| 关注点 | 设计 |
|---|---|
| 撤销边界 | 位于冲突对话框**确认之后**，包住整批写入（§4.3 `applyPlan`） |
| 快照超限 | `runConfigEdit` 在 >2 MB 时降级为"执行但不记录 + 提示"（[undo.js](../src/core/undo.js#L520-L523)）。批量导入若触发，toast 里明确写"本次导入过大，未进入撤销栈" |
| 事件 | `runConfigEdit` 提交后照常派发 `mm_config_changed`，App 侧订阅做 `refreshOutlinerIcons + markerVersion++ + scheduleSave`，只触发一次 |
| 落盘 | 仍保留一次显式 `saveConfig()`（导入属于必须立即落盘的场景；面板可能未挂载，不能只依赖 `scheduleSave`） |
| 嵌套 | 内层 `runConfigEdit` 保留，但即使被拆开也不会再产生多条记录（外层已是同步闭合的） |

### 4.7 兼容包装

| 旧导出 | 新实现 |
|---|---|
| `importSingleFile(filePath, fileName, rawContent, batchAction)` | `importParts([{path, name, content}])`（`batchAction` 映射为 `options.action`） |
| `importMultipleFiles(files)` | `importParts(files)` |
| `importPartFromPath(filePath)` | 读盘后 `importParts([...])` |
| `registerDragImport` / `unregisterDragImport` | 内部改为直接调 `importParts(jsonFiles)`；删除 `jsonFiles.length === 1` 分支与外层 `runConfigEdit('批量导入零件')` |

拖拽路径同时删掉 `console.log('[MM][DragImport] ...')` 的裸日志（与上一次 `chore(log)` 同方向，避免又一次噪音回潮）。

## 5. 交互语义约定

| 场景 | 行为 |
|---|---|
| 整批无冲突、全部成功 | 一条 toast：`已导入 5 个零件` |
| 部分文件解析失败 | 其余照常导入；toast：`已导入 3 个，2 个失败（a.json、b.json）`；失败原因进日志 |
| 全部解析失败 | 不产生撤销记录，只弹错误 toast |
| 存在冲突 | 只弹 1 个对话框；选择对**整批**生效；未冲突的文件总是导入 |
| 全部跳过 | 无撤销记录、无落盘、无刷新，toast `已跳过 3 个` |
| 有骨骼未解析 | 汇总进同一条 toast：`已导入 4 个零件（7 个骨骼未在大纲树中找到）` |
| 撤销 | 整批一条：`Ctrl+Z` 全退，`Ctrl+Y` 全回 |
| 批内同名文件 | 按出现顺序自动重命名，汇总提示 `a.json、a(1).json` 的最终 ID |

## 6. 边界与失败处理

| 边界 | 处理 |
|---|---|
| Web 版（无 `fs`） | 完全依赖 `FileResult.content`，不落 `readTextFile`；`normalizeInputs` 在 `content` 缺失且无 `path` 时记为失败 |
| 桌面端文件被锁/被删 | Blockbench 的 `readFile` 在 `readFileSync` 抛错时不会自增计数，`callback` 可能永不触发（[file_system.ts:213-249](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L213-L249)）。概率低，本次**不绕过** BB 的读取，但在 README/文档中记录；若现场复现，再考虑加超时提示 |
| 同一批 20+ 文件 | 一次性写入 + 一次快照，性能优于现在的 N 次快照 |
| 2 MB 快照上限 | 见 §4.6；toast 明确提示未进撤销栈 |
| `config` 中途变化（切换项目） | `importParts` 在入口取一次 `getConfig()`；冲突对话框确认后再取一次，缺失则放弃并提示 |
| 非法 partId | 单文件失败不阻断整批；toast 列出文件名与规则 |

## 7. 测试计划

### 7.1 新增单测 `test/import/import_plan.test.js`

纯函数，无需 Blockbench 桩：

| 用例 | 断言 |
|---|---|
| 3 个合法文件 | `entries.length === 3`，`failures` 为空，`conflictIds` 为空 |
| 混入坏 JSON | 该文件进 `failures(bad_json)`，其余 2 个仍在 `entries` |
| 非法 partId（`..`、`A Upper`、`CON`） | 进 `failures(bad_part_id)`，不写入 |
| 与现有 `parts` 冲突 | `conflictIds` 含该 ID，`entries[i].conflict === true` |
| 批内同名（不同目录 `a.json` ×2） | 第二个 `finalId === 'a_1'`，`conflictIds` 含 `a` |
| `resolvePlan(plan, 'skip')` | 冲突项 `action = 'skip'`，非冲突项仍为 `overwrite` |
| `resolvePlan(plan, 'rename')` | 冲突项 `finalId` 唯一，且不与批内其他 `finalId` 重复 |
| 输入数组为空 / 全非 json | `entries` 与 `failures` 都为空（静默） |

### 7.2 手动验收（必须过）

1. 菜单选 3 个正常 JSON → 全部导入；`Ctrl+Z` **一次**回退 3 个；`Ctrl+Y` 一次恢复。
2. 其中 1 个改名成已存在的 partId → **只弹 1 个**对话框；选「全部覆盖」后 3 个都进；`Ctrl+Z` 一次全退。
3. 选「全部跳过」→ 冲突文件被跳过、未冲突文件导入；toast 计数正确。
4. 选「全部重命名」→ 冲突文件得到 `_1` 后缀，原文件不动。
5. 混入 1 个坏 JSON → 其余正常导入；toast 指出失败文件。
6. 拖拽 3 个文件（含 1 个冲突）→ 行为与菜单完全一致；`Ctrl+Z` 一次全退。
7. 全选后取消选择 → 无 toast、无撤销记录。
8. `bun test` 251 项不回归（新增用例另计）。
9. `npm run build` 后 `dist` 中不再出现 `require("electron")` 与 `read_mode`。

## 8. 风险与已知限制

### 8.1 Blockbench 读取的计数 bug（外部）

见 §6。属于 Blockbench 自身缺陷，不在本次修复范围；若现场出现"选了文件没反应"，优先怀疑被锁文件。

### 8.2 批量快照过大

一次导入几十个大零件可能超过 2 MB 上限 → 降级为"不记录撤销"。这是**既有**行为，本次只改进提示文案；若确实常见，后续再做分片（每 N 个一条记录）。

### 8.3 冲突判定只看 partId

不比较内容差异；`overwrite` 仍是"整件替换"。与现状一致，不在本次扩展。

### 8.4 分层遗留：导入写入绕过 `ops/`

导入写入目前直接调 `undo.runConfigEdit`（[drag_import.js](../src/import/drag_import.js#L176-L179)），与 `ops.importPart`（[part.js](../src/ops/part.js#L76-L127)）是两条不同管线：

- 导入管线：`PartCodec.decode` + `resolveBoneReferences`（按骨骼名反查建 marker）；
- `ops` 管线：`doc` 投影 + `shared.applyProjection`（marker 能力通过 `doc/ports` 注入）。

按 [AGENTS.md](../AGENTS.md) 的约定，结构性动作应当收敛到 `ops/`。但切换管线会改变 marker 建立与字段归一化的细节，属于独立重构。**本次保持现状**，建议后续单独出计划（`ops.importParts`）再收编。

### 8.5 版本号

功能修复 → `0.5.3` 升到 `0.5.4`；`scripts/build.js` 会自动同步 `bbplugin.json`。`dist/` 已入库，需一并重建提交。
