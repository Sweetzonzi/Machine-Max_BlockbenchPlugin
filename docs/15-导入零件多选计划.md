## 1. 背景与目标

### 1.1 现状

| 项 | 现状 | 位置 |
|---|---|---|
| 菜单入口 | 「导入零件 JSON…」单个菜单项 | [menu.js](../src/ui/menu.js#L70-L124) |
| 文件选择 | 桌面端先试 `require('electron').remote.dialog`（**永不成功**），再回落 `Blockbench.import` | [menu.js](../src/ui/menu.js#L81-L121) |
| 多选 | **不支持**：回落调用没传 `multiple` | [menu.js](../src/ui/menu.js#L108-L111) |
| 单文件导入 | 解析 → 冲突对话框 → 写入 → 落盘 → 刷新 → toast | [drag_import.js](../src/import/drag_import.js#L70-L215) |
| 多文件导入 | 只有拖拽路径会走到；菜单是 `for` 循环逐文件调 `importPartFromPath` | [menu.js](../src/ui/menu.js#L98-L120)、[drag_import.js](../src/import/drag_import.js#L226-L305) |
| 撤销粒度 | 菜单：每文件一条；拖拽：**有冲突时**退化为每文件一条 | [drag_import.js](../src/import/drag_import.js#L388-L393) |

### 1.2 目标

1. **桌面端**文件选择器支持一次选多个 `.json`（插件 `variant: 'desktop'`，见 [plugin.js](../src/plugin.js#L25-L31) 与 `bbplugin.json` 的 `"target": "desktop"`）。
2. 整批导入只产生**一条**撤销记录：`Ctrl+Z` 一次全退，`Ctrl+Y` 一次全回。
3. 冲突**只询问一次**，策略对整批生效（覆盖 / 跳过 / 自动重命名 / 取消）。
4. 单个文件失败（坏 JSON / 非零件定义 / 非法 partId / 读盘失败 / 空内容）不中断整批，其余照常导入并**一条**汇总提示。
5. 菜单多选与拖拽复用同一条编排管线，行为一致。
6. 模块只保留**有调用方**的导出：`registerDragImport` / `unregisterDragImport` / 新增 `importParts`。现有 `importSingleFile` / `importPartFromPath` 在菜单改造后零调用方（详见 §4.7），一并删除。

### 1.3 非目标

- **不动**导入的解析管线：仍是 `PartCodec.decode` + `resolveBoneReferences`，不切到 `ops.importPart` 的 `doc` 投影通道（两条管线语义不同，见 §8.4）。
- 不做"导入整个目录"、"从内容包拖入"等新入口。
- **Web 端不列入验收**（插件声明 `variant: 'desktop'`，Blockbench 不会在 Web 版提供它）。代码保持 Web 安全（用 `FileResult.content`，不依赖 `path`），但这是防御性兼容，不是目标。
- 不新增 MCP 工具；`mcp/tools.js` 的 `import_part` 走 `ops.importPart`，本次不受影响。
- 不做"内容查重"（同内容不同文件名视为两个零件）。
- 不给 `runConfigEdit` 增加"是否入栈"的返回位（属 core 改动，见 §4.6）。

## 2. 调研结论：为什么现在只能单选

### 2.1 Electron 原生分支是死代码

[menu.js](../src/ui/menu.js#L81-L105) 的逻辑是"先拿 `require('electron').remote`，有就调原生 `showOpenDialog`（这里其实已经写了 `multiSelections`）"。

这个分支在 Blockbench 5.x 下**永远进不去**，两个独立原因：

1. **API 不存在**：Blockbench 5.0.7 依赖 Electron `^38.1.0`（`package.json`），`remote` 模块自 Electron 14 起已移除。
2. **模块被白名单拦截**：插件的 `require` 是 Blockbench 的 scoped require（`new Function('require', code)` 注入，见 [plugin_loader.ts:678-689](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/plugin_loader.ts#L678-L689)），只放行
   `SAFE_APIS`（`path/crypto/events/zlib/timers/url/string_decoder/querystring/constants/buffer`）与
   `REQUESTABLE_APIS`（`fs/process/child_process/https/net/tls/util/os/v8/dialog/clipboard`），
   其余模块直接 `throw 'The module "electron" is not supported'`
   （[native_apis.ts:33-97](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/native_apis.ts#L33-L97)）。
   `'electron'` 不在名单里 → `catch` → `remote = null`。

所以在装好的插件里，"带 `multiSelections` 的原生对话框"这 20 多行是纯粹的噪音代码，每次点击还要抛一次异常再吞掉。

### 2.2 回落分支缺少 `multiple`

[menu.js](../src/ui/menu.js#L108-L121) 的回落调用只传了 `extensions`、`type`、`read_mode`。

Blockbench 的 `Blockbench.import(options, callback)`（别名 `importFile`，[api.ts:374-378](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/api.ts#L374-L378)）的 `ImportOptions` 明确支持多选：

```ts
// js/file_system.ts:53-74 / 81-149
multiple?: boolean          // 桌面端 push('multiSelections')；Web 端 input.multiple = true
readtype?: 'buffer'|'binary'|'text'|'image'|'none'|((file) => ReadType)
resource_id?: ResourceID    // 记住该资源类型上次打开的目录（StateMemory 'dialog_paths'）
```

Blockbench 自己也这么用（[io.js:526-541](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/io/io.js#L526-L541)）。我们没传 → 原生对话框就是单选。

**结论：多选能力一直是现成的，只是没打开。**

### 2.3 顺带发现的两个小问题

| 问题 | 说明 | 影响 |
|---|---|---|
| `read_mode` 是笔误 | 选项真名是 `readtype`；不过默认值就是 `text`（[file_system.ts:179-181](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L179-L181)），所以现在"碰巧"是对的 | 无功能影响，但会误导后续维护 |
| 已读到的内容被丢弃 | 回调里 `FileResult` 已含 `content`（[file_system.ts:241-245](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L241-L245)），代码却拿 `files[i].path` 再走 `importPartFromPath` 读一次盘 | 多一次 IO；Web 端 `path` 只是文件名（[file_system.ts:267-272](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L267-L272)），重读必失败 |

### 2.4 批量语义现状（比"多选"更值得修）

即使只加一个 `multiple: true`，现在的实现也会把批量导入做成"一串独立操作"：

| 场景 | 现状 | 问题 |
|---|---|---|
| 菜单选 3 个文件 | `for` 循环逐文件 `importPartFromPath` | 3 条撤销记录、3 次 `saveConfig()`、3 次 `refreshOutlinerIcons()`、3 个 toast |
| 3 个文件里有 1 个 ID 已存在 | 每个冲突文件各弹一个 async Dialog | 对话框叠栈；用户要连续点两次 |
| 拖拽 3 个文件（无冲突） | 外层 `runConfigEdit('批量导入零件')` + 内层嵌套 | 撤销正确（一次回退整批）✅ |
| 拖拽 3 个文件（有冲突） | 外层 edit 在对话框确认前就 `mutate` 返回 → 空快照被丢弃；真正写入发生在对话框回调里 | **撤销退化为每文件一条**，与注释"一次 Ctrl+Z 回退整批"不符 |

第 4 条是实现细节导致的：`runConfigEdit` 的 `mutate` 必须同步完成（[undo.js](../src/core/undo.js#L491-L569)），而 `showConflictDialog` 是异步的（[conflict_dialog.js](../src/import/conflict_dialog.js#L54-L78)）。[docs/13 风险表](./13-业务逻辑层与配置文档API.md#L1454) 已经登记过这条缺陷与正确方向（"冲突决策提前到开记录前"）。

## 3. 方案对比

| 方案 | 改动量 | 多选 | 撤销粒度 | 冲突交互 | 备注 |
|---|---|---|---|---|---|
| **A. 只加 `multiple: true`** | ~3 行 | ✅ | 每文件一条 | 仍逐文件弹窗 | 能选多，但批量体验与撤销都不合格 |
| **B. 统一入口 + 批量编排**（推荐） | ~220 行 | ✅ | 整批一条 | 一次对话框，策略对整批生效 | 菜单与拖拽共用一条管线 |
| **C. 导入预览对话框** | ~400 行 | ✅ | 整批一条 | 逐项勾选 + 逐项策略 | 体验最好，建议作为后续迭代 |
| **D. `require('dialog')` 走原生对话框** | ~40 行 | ✅ | 取决于编排 | 同 A/B | 需要额外申请"打开原生对话框"权限，多一次授权弹窗；`Blockbench.import` 已够用 |

**选 B**。理由：

- `Blockbench.import` 已覆盖桌面端多选，且支持 `resource_id` 记住上次目录，没有理由绕开它去申请新权限（排 D）；
- 多选只是入口问题，真正的痛点是撤销粒度和冲突交互（A 不解决）；
- C 的信息量对"导入零件"这种低频操作用不上，先留接口（`resolvePlan` 的输出天然就是预览数据）。

## 4. 详细设计

### 4.0 状态模型与动作真值表（实现与测试的共同规格）

每个文件先归到三种状态之一：

| 状态 | 判据 |
|---|---|
| `new` | `partId` 不在 `config.parts`，且本批更早的条目没有同 `partId` |
| `existing` | `partId` 在 `config.parts` |
| `duplicate` | 本批更早的条目已有同 `partId`（**不论** `config.parts` 是否也有） |

`duplicate` 不弹框、不参与 `existingIds`；它**跟随同批 leader 的有效动作**（leader 写入则改名，leader 跳过/取消则同跳），与用户在对话框里选什么无关。

| # | 状态 | 用户选择 | `action` | `finalId` | 写入 | 说明 |
|---|---|---|---|---|---|---|
| 1 | new | 无冲突不弹框 | `create` | `partId` | 是（新增） | |
| 2 | new | 选了 skip（因批内别处有冲突） | `create` | `partId` | 是 | `skip` 只作用于 `existing`，不牵连新增文件 |
| 3 | existing | overwrite | `overwrite` | `partId` | 是（整件替换） | |
| 4 | existing | skip | `skip` | `partId` | 否 | |
| 5 | existing | rename | `rename` | `reserve(partId)` | 是（新 key） | 如 `a` → `a_1` |
| 6 | existing | cancel | `cancel` | — | 否 | 整批不写；toast「已取消导入」 |
| 7 | duplicate（leader=new，或 leader=existing 选 overwrite/rename） | 任意 | `rename` | `reserve(partId)` | 是 | 首条写 `partId`，副本改名 |
| 8 | duplicate（leader=existing 选 skip） | skip | `skip` | — | 否 | 避免出现"只有 `a_1` 没有 `a`" |
| 9 | duplicate（leader=existing 选 cancel） | cancel | `cancel` | — | 否 | |

`resolvePlan` 的后置条件（写成可复用的断言函数，§7.1 每条用例都调用）：

1. `written = entries.filter(e => e.action !== 'skip' && e.action !== 'cancel')`；
2. `written` 的 `finalId` **两两不同**，且每个都通过 `keys.isSafePartId`；
3. `written` 中**至多一条**的 `finalId` 属于 `existingIds`（覆盖不会连带覆盖两次）；
4. `state === 'new'` 的条目 `finalId === partId`；
5. `action === 'cancel'` 时 `written.length === 0`；
6. `written` 中每条的 `finalId` 都不为 `null`/`undefined`（`skip` / `cancel` 条目允许为 `null`；写入条目的非空由 `reservePartId` 契约保证）。

### 4.2 两个纯策略函数（`src/services/import_plan.js`）

#### 4.2.1 失败归属与输入契约

失败分两段产生，**`planImports` 永远看不到 I/O 结果**：

| 阶段 | 位置 | 失败类型 |
|---|---|---|
| 归一化（唯一 I/O 点） | `drag_import.normalizeInputs(files)` | `read_failed`、`empty_content` |
| 纯策略 | `import_plan.planImports(inputs, existingParts)` | `bad_json`、`bad_part`、`bad_part_id` |

```js
// drag_import.js
/** @returns {{inputs: Array<{name, content, path?}>, failures: Array<{fileName, reason}>}} */
function normalizeInputs(files) { ... }   // 有 content 不读盘；content 缺失才 readTextFile(path)

// services/import_plan.js
/**
 * @param {Array<{name: string, content: string, path?: string}>} inputs  // 只含"有内容"的文件
 * @param {Object<string, any>} existingParts                             // config.parts（只读，不修改）
 * @returns {{
 *   entries: Array<{
 *     fileName: string,
 *     partId: string,
 *     partConfig: Object,
 *     state: 'new'|'existing'|'duplicate',
 *     leaderIndex: number|null   // entries 数组下标（不是原始 files 下标）；仅 duplicate
 *   }>,
 *   failures: Array<{fileName: string, reason: 'bad_json'|'bad_part'|'bad_part_id', detail?: string}>,
 *   existingIds: string[],      // 去重，仅用于冲突对话框
 *   duplicateIds: string[]      // 去重，仅用于汇总提示
 * }}
 */
function planImports(inputs, existingParts) { ... }
```

`leaderIndex` 的基准写死为 **`entries` 数组下标**：失败文件不进 `entries`，所以它与"用户选中的第几个文件"不是一回事。

#### 4.2.2 解析与校验规则

| 输入 | 结果 |
|---|---|
| 扩展名不是 `.json`（大小写不敏感） | 静默忽略（在 `normalizeInputs` 里过滤） |
| `content === ''` | `empty_content`（`normalizeInputs` 产出） |
| 无 `content` 且读盘抛错 | `read_failed`（`normalizeInputs` 产出） |
| `parseJSONWithComments` 抛错 | `bad_json` |
| `PartCodec.decode` 抛错（非对象/数组/字段类型不符） | `bad_part` |
| 解码后 `variants` **不是非空对象** | `bad_part` |
| `keys.isSafePartId(partId)` 不通过 | `bad_part_id` |

**"`variants` 非空"的依据是导出闸门本身**：[validate.js](../src/services/validate.js#L251-L257) 已经把"零件没有定义变体"判为 `MISSING_REQUIRED` error。导入侧用同一条判据，就不会出现"导进来了但导出时必被拦"的零件。

这也解释了为什么必须显式判：`PartCodec` 的 **9 个字段全部带默认值**（[part_codec.js](../src/codec/codecs/part_codec.js#L37-L56)；文件头注释写"12 字段"是存量笔误，本次顺手改为 9），而 `Codec.record.decode` 宽松到"任何对象都能解出全默认零件并保留未知字段"（[Codec.js](../src/codec/Codec.js#L412-L436)）。误选一个 connector JSON 不会抛错，会静默写成"零变体空零件"。

**单变体简写必须被接受**：导出的单变体零件是 `{"model": "...", "textures": {...}}` 形态，`Codec.either` 用 `typeof raw.model === 'string'` 判定并包装成 `{default: variant}`（[Codec.js](../src/codec/Codec.js#L575-L606)），因此 `variants` 仍是非空对象。**必须有用例钉住**，否则"非空"判据可能被后续改动误伤。

#### 4.2.3 `resolvePlan(plan, action)`

```js
/**
 * @param {ReturnType<typeof planImports>} plan
 * @param {'overwrite'|'skip'|'rename'|'cancel'} action
 * @returns {{ entries: Array<{...planEntry, action: string, finalId: string|null}>,
 *             cancelled: boolean }}
 */
function resolvePlan(plan, action) { ... }
```

**分配算法（两遍，v2 的单遍写法有 P0 缺陷）**：

```
① used = new Set(existingIds)
② 第一遍：把所有 state === 'new' 的条目钉死 finalId = partId，并 used.add(partId)
③ 第二遍：按 entries 顺序处理 existing / duplicate
     existing + overwrite → finalId = partId
     existing + skip      → finalId = partId（不写）
     existing + rename    → finalId = reservePartId(partId, used)
     duplicate            → 看 leader 的已决 action：
                            skip/cancel → 同 skip/cancel
                            否则 → reservePartId(partId, used)
     得到 finalId 时 used.add(finalId)
④ action === 'cancel' → 全部 action='cancel'，cancelled=true
```

为什么必须两遍：**`new` 条目的 `partId` 在分配前既不在 `existingIds`、也还没被"分配"**。v2 的单遍写法下，最小反例是

```
config.parts 已有 b；本批选 b.json（existing）+ b_1.json（new）；用户选"全部重命名"
v2（单遍）：处理 existing b → used={b} → 得 b_1；再处理 new b_1 → finalId=b_1
            ⇒ 两条 entry 都写 b_1，后者覆盖前者，且违反后置条件 2
v3（两遍）：先钉死 new b_1 → used={b,b_1}；再 reserve('b') → b_2
            ⇒ 写入 {b_2, b_1}，唯一且无覆盖
```

副作用是编号会"跳号"：上例中原零件改名为 `b_2` 而不是 `b_1`。这是正确取舍（不撞占位），但必须在用户可见文案里说明（§5）。

#### 4.2.4 `reservePartId(base, used)`（`src/doc/keys.js`）

```js
keys.reservePartId('a'.repeat(128), usedSet)  // → 126 长度 + '_1'，不越 128 上限
```

```js
function applyPlan(plan, action, failures) {
    var resolved = importPlan.resolvePlan(plan, action);
    if (resolved.cancelled) { showToast('已取消导入'); return; }

    var config = getConfig();                     // 对话框是异步的：必须重新取
    if (!config) { showToast('项目已关闭，导入取消', 'warning'); return; }
    if (!config.parts) config.parts = {};

    var writable = resolved.entries.filter(function (e) {
        return e.action === 'create' || e.action === 'overwrite' || e.action === 'rename';
    });
    if (!writable.length) {                       // 全跳过：先判空，不进撤销栈
        showToast(summaryText({ written: 0, failures: failures }), 'info');
        return;
    }

    var unresolvedTotal = 0;
    undo.runConfigEdit('导入 ' + writable.length + ' 个零件', function () {
        for (var i = 0; i < writable.length; i++) {
            var e = writable[i];
            config.parts[e.finalId] = e.partConfig;
            resolveBoneReferences(config, e.finalId);
            unresolvedTotal += (e.partConfig._unresolved_bones || []).length;
        }
    });

    // 视图：仅当当前活动零件失效时才切到第一个新零件（_uiState 不进撤销栈）
    var active = config._uiState && config._uiState.activePartId;
    if (!active || !config.parts[active]) {
        ops.setActive(config, { partId: writable[0].finalId, source: 'import' });
    }

    flushSave();
    try { require('../mode/icons.js').refreshOutlinerIcons(); } catch (e) { /* 非零件模式 */ }
    showToast(summaryText({
        written: writable.length,
        failures: failures,
        unresolved: unresolvedTotal,
    }), unresolvedTotal ? 'warning' : 'positive', 5000);
}
```

要点：

- **`runConfigEdit` 内只做同步写入**：不弹框、不读盘、不 toast、不落盘；
- **无嵌套 `runConfigEdit`**：撤销边界完全由 `applyPlan` 持有；
- **全跳过/全取消先判空**再决定开不开记录（不依赖 `_discardEmptyEntry` 兜底）；
- `flushSave()` 而不是 `saveConfig()`：`mm_config_changed` 已会 `scheduleSave()`（[App.vue.js](../src/ui/App.vue.js#L1780-L1796)），再 `saveConfig()` 就是写两次；
- 汇总 toast 只发一次：失败明细进日志，文件名超过 3 个截断。

```js
function summaryText(info) { /* {written, failures, unresolved} → '已导入 3 个零件（跳过 1，失败 2：a.json 等）' */ }
```

## 5. 交互语义约定

| 场景 | 行为 |
|---|---|
| 整批无冲突、全部成功 | 一条 toast：`已导入 5 个零件` |
| 部分文件解析失败 | 其余照常导入；toast：`已导入 3 个，2 个失败（a.json、b.json）`；失败原因进日志 |
| 全部解析失败 | 不产生撤销记录，一条错误 toast |
| 全部被扩展名过滤 / 空输入 | **静默**（不弹 toast） |
| 存在冲突 | **只弹 1 个**对话框；策略对整批生效 |
| 用户选 skip | **只跳过与现有零件冲突的文件**；本批新增零件、以及它们的同名副本仍按 leader 写入/改名 |
| 用户取消对话框 | **整批不写**（含未冲突文件），toast「已取消导入」 |
| 全部跳过（本批全部冲突） | 无撤销记录、无落盘、无刷新，toast `已跳过 3 个` |
| 批内同名文件 | 首条按规则处理，副本按 leader 结果自动改名；**改名会跳过本批其它文件占用的 ID**（例如本批有 `b_1.json` 时，`b` 重命名为 `b_2`） |
| 有骨骼未解析 | 汇总进同一条 toast：`已导入 4 个零件（7 个骨骼未在大纲树中找到）` |
| 撤销 | 整批一条：`Ctrl+Z` 全退，`Ctrl+Y` 全回 |

## 6. 边界与失败处理

| 边界 | 处理 |
|---|---|
| Web 端（无 `fs`） | 完全依赖 `FileResult.content`；`content` 缺失且无 `path` → `read_failed`。**仅作防御**，不列入验收 |
| `content` 不是字符串（Buffer 等） | 不兜成 `''`，传 `undefined` 让 `normalizeInputs` 用 `path` 回退（§4.4） |
| 桌面端文件被锁/被删 | Blockbench 的 `readFile` 在 `readFileSync` 抛错时不自增计数，`callback` 可能永不触发（[file_system.ts:213-249](https://github.com/JannisX11/blockbench/blob/v5.0.7/js/file_system.ts#L213-L249)）。不绕过 BB 读取；文档记录，现场复现再加超时提示 |
| 同一批 20+ 文件 | 一次写入 + 一次快照，优于现在的 N 次 |
| 2 MB 快照上限 | 沿用 `_runUnrecorded` 的既有节流提示（§4.6） |
| 切换项目（对话框期间） | `applyPlan` 内重新 `getConfig()`；缺失则放弃并提示 |
| 非法 partId | 单文件失败不阻断整批 |
| 128 长度上限 | `reservePartId` 截短 + `isSafePartId` 断言（§4.2.4） |
| 大小写/设备名 | `'A'` → 字符集拒绝；`'con'`、`'con_hull'` → 设备名/首段拒绝（`isSafePartId` 会查 `split('_')[0]`，[keys.js](../src/doc/keys.js#L106-L111)） |
| 单变体简写 | 走 `Codec.either` 的 `typeof raw.model === 'string'` 分支，`variants` 非空 → 正常导入 |
